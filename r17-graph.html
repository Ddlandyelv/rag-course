12第四部分 · Graph RAG·GRAPH

知识图谱怎么建、怎么用

Graph RAG 不是「更好的 RAG」，它换了一套数据结构。这一页讲清楚建图的五步、两种查询路径，以及为什么很多团队评估后决定不上。

前置：11 碎片化的天花板 读完接：13 从流水线到智能体 约 18 分钟
这一页在整条链路上的位置
对应环节Graph RAG · 架构与成本
不学卡在哪以为 Graph RAG 是「升级版」，不评估成本就上，建完发现维护不起。
它解决什么理解局部查询与全局查询的分工，能算出建图成本并做出取舍。

1离线：从文本里抽出「谁—做了什么—和谁」

Graph RAG 的离线流程比传统 RAG 多三步：

分块照常切块
→
实体抽取人名/公司/事件
→
关系抽取谁与谁、什么关系
→
建图节点 + 边
→
社区检测聚类成话题圈
→
社区摘要每圈写一份概述

前两步是常规操作，真正决定 Graph RAG 能力的是后两步：

社区检测（Community Detection）分层聚类

用图算法（常见是 Leiden）把关系紧密的节点聚成一个个「社区」。一个社区大致对应「一个话题圈」——比如某个项目的所有相关方。

这一步是自动的，不需要人工定义分类体系。

社区摘要（Community Summary）预压缩

对每个社区，让 LLM 读一遍其中所有实体与关系，写一段概述。摘要可以分层：小社区先摘要，再把小社区摘要合成大社区摘要。

这些摘要就是回答「全局性问题」的素材——它把分散的信息预先压缩了。

2在线：两种查询走两条路

查询类型走哪条路机制
局部查询
「张三负责哪个项目」		实体 → 邻居先在图里定位实体节点，取它的邻居与相关原文，拼成上下文
全局查询
「所有项目的共同风险」		社区摘要 → 分层汇总取出所有社区摘要，分批让模型各写一份小结，再汇总成总答案

全局查询本质上是 map-reduce：每个社区摘要各自 map 出一份局部结论，最后 reduce 成一个整体答案。这也是它敢说「覆盖全库」的原因——它读的不是原文，而是预先压好的摘要。

注意代价：全局查询要调用多次模型（社区数量越多调用越多），延迟和成本都显著高于一次普通检索。所以它通常用于「离线报告、周报生成」这类场景，不适合放进实时对话的主链路。

3建图的成本账

环节成本说明
实体/关系抽取高要对每一块文档跑一次 LLM，5000 块就是 5000 次调用
社区检测低纯图算法，秒级到分钟级
社区摘要中高每个社区一次 LLM 调用，且要分层重复
增量更新高文档变更要重新抽取、可能触发社区重算

一笔粗略的估算：10 万块文档的建图，LLM 调用成本可能是传统入库的几十倍，且每次全量重建都要重跑。这也是很多团队「评估后决定不上」的真实原因——不是效果不好，是成本结构不匹配。

4什么时候该上，什么时候不该

判断项偏向 Graph RAG偏向传统 RAG
查询类型总结、趋势、关系网占比高查具体事实、条款、数值
文档间关联强（人物、事件、项目互相引用）弱（各文档相对独立）
更新频率低（可接受定期重建）高（要求实时生效）
延迟要求宽松（报告、离线分析）严格（在线问答）
预算充足有限

一个务实的过渡方案：传统 RAG 为主，图谱只覆盖核心实体。比如只对「客户、产品、合同」三类实体建图，其余仍走向量检索。既拿到关系查询的能力，又不承担全量建图的成本。

本页要点

  1. Graph RAG 离线多做三步：关系抽取建图、社区检测、社区摘要。
  2. 局部查询走「实体→邻居」，全局查询走「社区摘要→分层汇总（map-reduce）」。
  3. 全局查询覆盖全库的代价是多次模型调用，延迟与成本都高。
  4. 建图成本可能是传统入库的几十倍，只在该类查询占比高、更新不频繁时才划算。

9自测

Q1Graph RAG 能回答全局性问题的关键是？
摘要相当于一次「预压缩」：把分散在几百块里的信息提前归纳。查询时不需要再去检索原文，而是对摘要做分层汇总。
Q2社区摘要的主要成本在哪？
社区数量可能成百上千，每个都要一次 LLM 调用；分层汇总还要再跑一轮。这是 Graph RAG 成本高于传统 RAG 的主要来源之一。
Q3文档每天更新、要求实时生效的场景，为什么不适合全量 Graph RAG？
建图是一次「重加工」，不像向量索引那样容易增量维护。高频更新的知识库更适合传统 RAG，或只用图谱覆盖稳定的核心实体。
