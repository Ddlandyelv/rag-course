向量库与索引结构

这一步看起来只是「选个数据库」，但索引结构决定了检索的召回率和延迟，元数据过滤决定了权限和时效能不能做。

对应环节离线第 4 步 · 入库
不学卡在哪把向量库当成普通数据库用，不理解近似检索的取舍，也不知道过滤条件该放在哪一层。
它解决什么能根据数据量与延迟要求选索引，并知道元数据过滤必须下推到检索层。

1向量库不是「带索引的数据库」

普通数据库解决的是「精确查找」：WHERE id = 123，要么命中要么没有。向量库解决的是「最近邻查找」：给我和这个向量最像的 K 条。这两件事的底层算法完全不同。

向量数据库要做的事最近邻检索

在几百万到几十亿条高维向量里，用毫秒级时间找出与查询向量最相似的 K 条，同时支持按元数据过滤（部门、时间、类型）。

难点在于：高维空间里没有「树」这种结构能有效剪枝（维度灾难），所以必须用近似算法——牺牲一点点召回率，换几个数量级的速度。

2四种索引结构，一个取舍

索引原理一句话召回率速度内存
Flat（暴力）和每一条都比一遍100%（精确）最慢低
IVF（倒排）先聚类，只在最近的几个簇里找中高，可调快中
HNSW（图）建一张近邻图，像走高速一样跳着找高很快高
PQ（量化）把向量压缩成短码，用近似距离比较低最快很低

实际系统经常组合使用：HNSW + PQ（图索引 + 向量压缩），在大规模下兼顾速度与内存。

选择的关键不是「哪个最好」，而是你的数据量和延迟要求：10 万条以内用 Flat 就够（精确且简单）；百万级用 HNSW；上亿级才需要认真考虑量化与分片。

3元数据过滤：一个容易被低估的坑

真实查询几乎都带过滤条件：「近三个月」「本部门」「只看产品文档」。这就带来一个设计问题：先过滤再检索，还是先检索再过滤？

策略做法风险
先检索后过滤先取 top-100，再按条件筛筛完可能只剩 3 条，甚至全被筛掉
先过滤后检索先按条件缩小范围，再在子集里找最近邻需要索引支持「带过滤的检索」，否则很慢
混合（主流）过滤条件下推到索引层，边走图边判断实现复杂，但对效果和性能都友好

如果数据库不支持带过滤的近似检索，一个实用兜底是：把 top-K 放大（如 100），再过滤到目标数量。代价是延迟上升，但至少不会返回空结果。

4选型：先看部署形态，再看性能

方案形态适合
pgvectorPostgreSQL 扩展已有 PG、数据量百万级以内、想少一个组件
Chroma嵌入式 / 轻量服务原型验证、单机小规模
Milvus分布式专用向量库亿级规模、需要水平扩展
Qdrant / Weaviate专用向量库需要强过滤、混合检索、多租户
Elasticsearch / OpenSearch搜索引擎的向量能力已有 ES，想要关键词 + 向量一体
FAISS库（非服务）离线批处理、自己搭服务

一个务实的判断顺序：数据量 → 是否要混合检索 → 团队已有的技术栈。多数团队最后一轮比较下来，选的是「已有组件的向量能力」而不是引入新组件——少一个需要运维的系统，比多 20% 的性能更值。

本页要点

  1. 向量库解决的是近似最近邻检索，不是精确查找。
  2. 四种索引（Flat/IVF/HNSW/PQ）在召回率、速度、内存之间取舍，常组合使用。
  3. 10 万条以内 Flat 就够；百万级用 HNSW；上亿才需要认真做量化与分片。
  4. 元数据过滤要尽量下推到索引层，否则「先检索后过滤」很容易筛空。

9自测

Q1为什么向量检索几乎都用「近似」算法？
经典的树形索引在低维有效，高维会退化成全扫描（维度灾难）。近似算法牺牲少量召回率，换来几个数量级的速度提升，工程上这笔交易划算。
Q2「先检索 top-100 再按部门过滤」最可能出的问题是？
这正是需要「带过滤的检索」（filtered search）的原因：把条件下推到索引层，在符合条件的子集里找最近邻，而不是先取全局 top-K 再筛。
Q3数据量约 50 万条、要求精确召回、可接受稍慢，优先选？
50 万条用 Flat 仍在可接受范围，且能拿到 100% 召回，省掉了调参和精度损失。数据量再上一个数量级才需要引入近似索引。
