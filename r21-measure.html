怎么测：数据集与裁判

指标定了，接下来是工程问题：测试集从哪来、谁来打分、结果怎么用。这一页给出可执行的一套流程。

1先有测试集，才谈得上评估

没有测试集，所有「效果变好了」都是感觉。而手工写 200 道题的成本很高，所以工业界普遍用自动合成：

  1. 从知识库里随机取一块作为「根上下文」；
  2. 检索它相邻的 K 块，拼成一段更完整的上下文；
  3. 让模型基于这段上下文出题 + 出答案；
  4. 重复 N 次，得到 N 条「问题 + 标准答案 + 依据片段」的三元组。

合成时要加约束，否则会产出一堆低质题：

约束目的
问题必须脱离上下文也能被人类读懂避免出现「根据上文，它指什么」这类废题
答案不能包含链接、代码块避免无法判分
不要在问题里出现「根据提供的资料」避免泄露题型
问题控制在 10 个词以内、尽可能具体避免过于宽泛、无法判定对错
避免用「和」连接多个问题避免一个问题包含多个子目标，难以判定

合成题目的质量决定了评估的天花板。所以合成之后必须人工抽检 10%–20%，把明显不合理的剔掉，否则你会一直在优化一个错误的目标。

2谁来打分：人还是模型

方式成本一致性适合
人工标注极高中（不同人标准不同）建立基准、校准模型裁判
LLM 裁判低高（同一提示下稳定）批量回归测试、日常迭代
规则匹配极低完美但僵硬有标准答案的短答案题
用户反馈零（但需埋点）真实但有偏线上效果监控

实践中的组合是：人工标 100–200 条作为「黄金集」，用它校准 LLM 裁判的提示与阈值，之后所有迭代都用 LLM 裁判跑全量。

校准这一步不能省。做法是：让 LLM 裁判和人工在同一批样本上打分，计算一致性（如 Spearman 相关）。如果一致性低于 0.7，说明裁判提示写得不好，结论不可信。

3怎么用结果定位问题

有了三个指标，定位就变成查表：

上下文相关性忠实度答案相关性判断先改哪里
低——检索没找对改写、混合检索、重排
高低—资料对了，模型在编提示词约束、降低温度、换更强模型
高高低资料对、没编，但答非所问检查提示词是否误解了问题、检查是否被无关段落带偏
高高高指标都好但用户不满查时效、格式、覆盖率

这张表的价值在于：它把「优化」变成了「按指标查方向」，而不是每次改一个地方然后祈祷。

4回归测试：改一个参数，跑一遍全集

RAG 的参数是互相影响的：改了 chunk_size，检索分布会变；换了嵌入模型，阈值要重定；加了重排，top-K 也要调。所以每次改动都应该：

  1. 固定测试集（同一批问题）；
  2. 跑全量，记录三个指标；
  3. 和上一版对比，看是整体提升还是某些类型提升、某些类型变差。

第三步最关键。只看平均值会掩盖问题：如果总分涨了 2 分，但「多跳类问题」掉了 10 分，这个改动在真实场景里可能是负面的。所以测试集要按问题类型分层统计。

一个最低成本的实践：把每次改动的指标记进一张表（版本 / 参数 / 三个指标 / 分层结果）。两三周后回头看，你会非常清楚哪些改动真的有效——这比任何直觉都可靠。

本页要点

  1. 测试集可以自动合成，但必须人工抽检，否则在优化一个错误的目标。
  2. 人工标注建黄金集，校准 LLM 裁判，之后用裁判跑全量。
  3. 三指标的组合能直接定位「检索错 / 生成编 / 答非所问 / 都不对」。
  4. 每次改动跑同一批测试集，并按问题类型分层看，不要只看平均值。

9自测

Q1为什么合成测试集后还要人工抽检？
合成题的典型缺陷是「问题脱离上下文读不懂」「答案无法判定对错」。如果测试集本身有问题，指标再漂亮也不代表真实效果。
Q2三个指标里「上下文相关性高、忠实度高、答案相关性低」，最可能的问题是？
前两个指标说明「资料找对了且答案忠于资料」，答案相关性低说明「答的不是用户问的」。常见原因是提示词让模型误解了任务，或被某段次要资料带偏。
Q3为什么评估结果要按问题类型分层统计？
平均值上涨 2 分，可能来自简单问题提升 5 分、多跳问题下降 10 分。如果业务主要是多跳问题，这个改动实际上是负面的。
