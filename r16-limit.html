11第四部分 · Graph RAG·LIMIT

碎片化的天花板

前三部分的所有优化，都在「让检索更准」这条线上。但有一类问题，检索再准也答不了——因为答案不在任何一块文档里。

对应环节Graph RAG 的动机 · 什么时候该换架构
不学卡在哪把所有效果问题都归结为「检索不够准」，在全局性问题上反复调参却始终答不好。
它解决什么能识别三类「检索救不了」的问题，并判断是否值得上图谱。

1有些问题，检索几块永远答不了

传统 RAG 的所有优化（改写、混合、重排）都建立在同一个前提上：答案存在于某几块文档里，只要找得够准就能答。

但有一类问题，答案不在任何单独一块里，而在块与块之间的关系里。这类问题无论怎么优化检索都答不好，因为它们的失败不是「没找到」，而是「结构上不存在」。

「请总结过去三年所有项目失败的共同原因。」
「张三和李四之间是什么关系？」
「这个人的导师的导师是谁？」

2三类典型失效

类型问题长什么样为什么碎片检索答不了
全局性问题总结、归纳、趋势、「共同点是什么」答案分散在几百块里，任何 top-K 都只覆盖一小部分；模型看到的是局部切片，只能给出局部结论
多跳问题「A 的创始人后来创办了什么公司」需要先查 A 找到创始人，再拿这个人的名字查第二跳。单次检索做不到这种链式依赖
关系型问题「这几个人之间的商业关系网」关系没有被显式表达，只隐含在不同文档的叙述里，向量相似度无法捕捉「谁和谁连接」

第一类最容易被低估。团队常以为「top-K 调大一点就行」，但把 K 从 5 调到 50，覆盖的仍然只是全库的百分之几，而且噪声急剧上升。

3一个具体的算例

假设知识库有 5000 块文档，要回答「所有项目的失败原因」。

做法覆盖范围结果
top-5 检索5 / 5000 = 0.1%只看到两三个项目，结论以偏概全
top-50 检索50 / 5000 = 1%仍缺 99% 的信息，且噪声挤占上下文
全量塞进上下文100%超出窗口，成本不可接受
分层归纳（map-reduce）100%可行，但要多次调用模型

最后一行就是 Graph RAG 全局查询的思路：不是「找最相关的几块」，而是「分层概括全部」。这已经超出了「检索」的范畴，属于「结构化归纳」。

4所以 Graph RAG 不是「更好的 RAG」

它换了一个问题：不再问「哪几块最相关」，而是问「这些内容之间的结构是什么」。

代价也很明确：

  • 建图要跑一遍 LLM 做实体关系抽取，成本远高于简单分块；
  • 图需要维护，文档更新时要同步更新实体与关系；
  • 查询延迟更高（要走图、要做多轮汇总）。

所以它不是「所有场景都该升级到 Graph RAG」，而是当你的问题类型里有大量全局/多跳/关系查询时才值得。如果 90% 的查询是「某个规定的具体数值」，传统 RAG 又快又准，没必要上图谱。

本页要点

  1. 传统 RAG 的前提是「答案在某几块文档里」，全局性、多跳、关系型问题不满足这个前提。
  2. 全局性问题靠调大 top-K 解决不了：覆盖比例仍然极低，噪声还会上升。
  3. Graph RAG 换的是问题：不问「哪块相关」，问「结构是什么」。
  4. 它的建图与维护成本明显更高，只在该类查询占比高时才值得上。

9自测

Q1「总结所有项目失败的共同原因」为什么调大 top-K 也解决不了？
这已经不是检索精度问题，而是覆盖率问题。要回答全局性问题，必须做「全量分层归纳」而不是「局部精确检索」。
Q2多跳问题（A 的创始人后来创办了什么）的难点是？
需要「查 A → 得到创始人姓名 → 用姓名再查」这样的串行过程。Agentic RAG 正是为这种多步推理设计的。
Q3什么情况下不该上 Graph RAG？
图谱的价值在结构与关系上。如果用户只是问「住宿标准是多少」，传统 RAG 又快又准，上图谱等于为少数场景付出全量成本。
