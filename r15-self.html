Self-RAG：要不要查，让它自己判断

无条件检索是标准 RAG 的默认行为，也是最容易被忽略的浪费。这一页讲 Self-RAG 怎么用反思标记把这个决定权交还给模型。

1一个朴素但昂贵的问题：每次都要检索吗

标准 RAG 是「无条件检索」：用户说「你好」，它也去查一遍知识库。这带来三个浪费：

  • 延迟：每次问答都多一次检索耗时；
  • 成本：多一次嵌入计算 + 向量检索；
  • 干扰：明明不需要资料的问题，硬塞几段不相关的内容，反而让回答变差。

更麻烦的是，检索回来的东西不一定有用。如果检索结果与问题无关，标准 RAG 仍会把它塞进提示词，然后模型基于无关内容硬答。

2Self-RAG 的核心：让模型自己判断

Self-RAG 的思路是训练模型在生成过程中输出反思标记（reflection token），用这些标记控制流程：

标记回答的问题取值
Retrieve这个问题需要检索吗？需要 / 不需要
IsREL这段资料与问题相关吗？相关 / 不相关
IsSUP我的这句话有资料支持吗？完全支持 / 部分支持 / 无支持
IsUSE这个答案对用户有用吗？1–5 分

流程因此变成：先判断要不要检索 → 检索后逐段判断相关性 → 生成时逐句判断是否有依据 → 最后判断整体是否有用。任一环节不满足，就重新检索或调整生成。

3和「用提示词让模型反思」的区别

有人会问：这不就是加一句「请检查你的答案是否有依据」吗？不是。差别在训练方式：

提示词式反思Self-RAG
实现在提示里要求模型自检专门训练模型输出反思标记
可靠性不稳定，模型可能「假装检查过」标记是训练出来的行为，可被解析和统计
可控性无法在流程中分支可以按标记决定是否重检索、是否拒答
成本无额外训练需要构造训练数据并微调

所以 Self-RAG 是一个训练方案，不是提示技巧。如果不想训练，可以用「提示词 + 多次调用」模拟它的流程（这就是 Agentic RAG 的雏形，见第 13、14 页），代价是延迟更高、稳定性更差。

4什么时候值得上 Self-RAG

它解决的问题很具体：查询类型混杂。

如果你的系统里，用户既会问「今天天气」（不需要知识库），也会问「报销标准」（需要），还会问「帮我写封邮件」（不需要检索但要生成），那无条件检索就是浪费。

反过来，如果系统只服务单一场景（比如只做制度问答），每次都必须检索，那么上 Self-RAG 的收益就很有限——判断「要不要检索」这一步永远返回「要」。

判断标准：如果「不需要检索」的请求占比超过 20%，就值得考虑；低于这个比例，优化别的环节更划算。

本页要点

  1. 无条件检索在「不需要资料」的请求上浪费延迟与成本，还会引入干扰。
  2. Self-RAG 训练模型输出四类反思标记：要不要检索、资料相关吗、句子有依据吗、答案有用吗。
  3. 它是训练方案而非提示技巧；不训练时可用多轮提示模拟，但延迟与稳定性都更差。
  4. 「不需要检索」的请求占比超过 20% 时，才值得投入 Self-RAG。

9自测

Q1Self-RAG 与「在提示词里要求模型自检」的关键差别是？
提示词式自检的结果是一段自然语言，难以稳定解析，模型也可能「走过场」。Self-RAG 把反思变成结构化标记，才能用来控制「是否重检索」「是否拒答」。
Q2什么情况下不适合上 Self-RAG？
如果「要不要检索」的判断永远返回「要」，这个模块就是纯开销。它的价值建立在「查询类型多样」这个前提上。
Q3IsSUP 标记检查的是？
四个标记各管一段：Retrieve 管要不要查，IsREL 管资料相不相关，IsSUP 管生成内容有没有依据（对应忠实度），IsUSE 管整体有没有用。
