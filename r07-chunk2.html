1四代分块方法

分块方法大致经过四代演进，每一代都在解决上一代的边界问题：

代际做法长处短处
① 固定长度每 N 个字符切一刀，可能带 overlap简单、快、长度可控必然切断句子，语义不完整
② 递归字符切分按「段落 → 句子 → 词 → 字符」的顺序逐级降级，尽量在语义边界断开通用性最好，是多数项目的默认选择不理解文档结构，对表格代码无感
③ 结构感知切分按 Markdown 标题、HTML 标签、代码块、LaTeX 环境切块与文档结构对齐，标题可作上下文依赖文档本身有结构；纯文本无能为力
④ 语义切分计算相邻句子的向量相似度，在「话题突变」处断开块内语义最连贯要先跑一遍嵌入，成本高、速度慢

LangChain 的 splitter 家族基本对应前三代：CharacterTextSplitter（第一代）、RecursiveCharacterTextSplitter（第二代）、MarkdownHeaderTextSplitter / HTMLHeaderTextSplitter / Language.PYTHON（第三代）。

2按文档类型选切分器

文档类型推荐方式理由
技术文档、说明书Markdown / HTML 标题切分标题本身就是语义边界，还能把标题拼进块里当上下文
合同、法规按条款编号切（正则）「第 3.2 条」是天然的、法律上有效的边界
代码库按函数 / 类切代码块被切断就完全不可读
论文、报告按章节 + 段落切章节结构清晰，段落是最小完整语义单元
聊天记录、工单按会话轮次切一问一答构成完整上下文，切开就失去意义
无结构长文本递归切分 + 适中 overlap没有结构可用，只能逐级降级

一个常被忽略的技巧：把标题拼进每个块。比如某块原文只有「一线城市 500 元，二线 350 元」，前面加上「出差管理制度 > 住宿标准」，这块的向量就会带上主题信息，检索「住宿标准」时命中率明显提高。

3三个工程参数

chunk_size参数 1

块的目标长度。按字符还是按 token 计算要统一——中文一个字符约等于 1–2 个 token，混用会导致实际长度失控。起点建议 300–500 字。

chunk_overlap参数 2

相邻块的重叠长度。10%–20% 是常见区间。重叠过大时需要在检索结果里做去重，否则 top-K 会被近似重复的内容占满。

分隔符优先级参数 3

递归切分时用哪一组分隔符。中文场景常见错误是沿用英文默认值（\n\n、\n、空格），结果中文句子因为「没有空格」被整段当成一个超长 token，最后只能硬切。

中文的递归分隔符建议写成：["\n\n", "\n", "。", "！", "？", "；", "，", ""]，让它在句号处就能断开。

4一个更进一步的思路：小块检索、大块召回

块大小的矛盾看起来无解：小了检索准但上下文不足，大了上下文全但检索钝。工程上有一个绕过它的办法——父子分块（也叫小块检索大块召回）：

  1. 把文档切成大段（父块，如整节 1500 字）；
  2. 每一段再切成小句（子块，如 200 字）；
  3. 向量库里只存子块的向量；
  4. 检索时用子块匹配，命中后返回它所属的父块给模型。

这样检索精度按小块的来，模型看到的是完整的父块，两个矛盾同时缓解。这个方案在第 08 页「检索中：混合检索与融合」里还会展开。

本页要点

  1. 四代分块：固定长度 → 递归降级 → 结构感知 → 语义切分，越往后越准也越贵。
  2. 按文档类型选切分器：标题、条款号、函数、会话轮次都是天然的语义边界。
  3. 把标题拼进块里，能显著提升主题类查询的命中率。
  4. 父子分块绕开了「小块准 / 大块全」的矛盾：检索用小块，返回用大块。

9自测

Q1中文场景沿用英文默认分隔符，最可能出的问题是？
递归切分依赖分隔符逐级降级。英文有空格可以作为最低一级的分隔符，中文没有，所以必须显式把「。！？；，」加进分隔符列表。
Q2「父子分块」解决的核心矛盾是？
用子块做向量匹配保证精度，命中后回溯父块保证上下文完整。代价是要维护两层索引的映射关系，且父块太大会重新引入噪声。
Q3把标题拼进块内容的主要好处是？
块原文可能只有具体数值，缺少主题词。拼上「出差管理制度 > 住宿标准」后，块的向量就带上了主题方向，用户问「住宿标准」时更容易命中。
