从流水线到智能体

前面十几页都在优化一条固定的链。这一页换个思路：把链交给一个会判断的智能体，让知识库变成它手里的工具之一。

不学卡在哪所有请求都走同一条流水线，闲聊被塞资料、新闻查内部库，效果和成本都吃亏。
它解决什么理解「控制流交给模型」的收益与代价，会用路由和工具描述约束它的行为。

1流水线的局限：一条路走到黑

前面所有优化，都还是在一条固定顺序的流水线上：改写 → 检索 → 重排 → 生成。无论什么问题，都走同一遍。

但真实请求的类型差别很大：

请求理想处理流水线实际做的
「你好」直接回复改写、检索、重排，塞进 3 段无关资料
「报销标准是多少」查规章制度库照做（但如果库里有多个来源，无法切换）
「今天行业有什么新闻」调联网搜索去查内部知识库，找不到
「帮我算一下这个公式」调计算器去查知识库，答不出

问题不在某一环做得不好，而在整条链没有「判断」这一步。Agentic RAG 的做法是把这条链交给一个能决策的智能体。

2把 RAG 变成 Agent 手里的一个工具

核心转变只有一句话：知识库不再是流程的一部分，而是智能体可以调用的一个工具。

传统 RAGAgentic RAG
流程固定：问题 → 检索 → 生成动态：模型自己决定调什么、调几次
知识源一个向量库多个工具：知识库、搜索引擎、数据库、计算器、API
控制者代码（if/else）模型（推理与选择）
失败处理无（一次不成就答错）可以换关键词重试、换数据源

3Routing：先判断该走哪条路

最常见也最容易落地的一步是路由：让模型（或一个小的分类器）判断请求类型，再分发到不同的处理路径。

用户输入
路由判断意图分类
知识库制度/产品问答
联网搜索实时信息
直接回复闲聊/常识

三条路径的差异很大：

  • 知识库：需要检索 + 引用；
  • 联网搜索：需要工具调用 + 结果清洗；
  • 直接回复：不检索，直接生成。

路由的价值不只是「不浪费检索」，更在于避免用错数据源——拿内部制度库去回答「今天有什么新闻」，只会得到一个过时的、看起来很像答案的错误回答。

实现上不一定要用大模型：如果意图类别固定且样本充足，一个小的分类模型（甚至关键词规则）更快更稳。能用规则解决的不要上模型，这是工程上的省钱原则。

4工具设计：比「让模型自由发挥」更重要

Agentic RAG 的效果，很大程度上取决于工具怎么描述。模型靠工具的名称和说明来决定调用谁，说明写得含糊，它就会乱调。

写法效果
search(query)太笼统，模型不知道搜什么、什么时候该搜
search_internal_docs(query, dept?)
「检索公司内部制度与产品文档。适用于关于公司规定、流程、产品参数的问题。」		好：说明了范围与适用场景

同样重要的是失败反馈：工具返回「没有找到」时，要把这句话如实传回给模型，而不是返回空字符串。模型看到「未找到」才会考虑换关键词或换工具；看到空字符串只会继续瞎猜。

本页要点

  1. 流水线的问题不是某一步差，而是没有「判断」，所有请求走同一条路。
  2. Agentic RAG 把知识库降级为工具之一，由模型决定调什么、调几次。
  3. 路由是最容易落地的一步，价值在于避免用错数据源，而不只是省检索。
  4. 工具的名称与说明决定了模型会不会正确调用；失败信息要如实回传。

9自测

Q1Agentic RAG 与传统 RAG 最本质的差别是？
传统 RAG 的顺序由代码决定，Agentic RAG 的顺序由模型推理决定。这带来灵活性（能重试、能换源），也带来不确定性（行为和成本更难预测）。
Q2路由模块最容易见效的价值是？
省一次检索是次要收益。主要收益是「不该查库的时候别查」——用错数据源会产出一个看似合理、实际完全无关的答案，比答不出来更糟。
Q3工具返回「未找到」时，为什么要如实回传这句话？
这是 Agent 设计里的通用原则：错误信息是给模型的输入，不是给日志的。含糊的失败信号会让模型误以为「查到了但内容为空」。
